## How colour findings land

Two constraints govern every colour recommendation in this document.

**Notation.** Recommendations are written in **OKLCH**, matching Harmoni's
oklch-first model and the direction the system is moving in. **Figma currently
holds hex**, so mirroring a value into a Figma variable means converting —
`oklch(0 0 0 / 0.1)` becomes `#0000001a`. That is a **representation gap, not
drift**; recorded here so a later token-sync pass doesn't "fix" one side to
match the other.

**Provenance.** Every palette colour is **generated by the Harmoni Rust engine
and pushed through the Figma plugin** — the ramps are engine output, not
hand-authored values. So a colour finding is only actionable if it can be
expressed as one of:

1. **An engine input change** — brand hue/chroma, the lightness curve, neutral
   tinting, the alpha curve. This is the route for anything affecting a ramp's
   shape or a whole family.
2. **A semantic re-binding** — pointing an Intent or Context token at a
   different step of an existing generated ramp. No engine change; the ramp is
   untouched and only the alias moves.
3. **A deliberate non-palette literal** — a value that is *not* a system colour
   and should never enter the ramp. Pass 01's image outline is the reference
   case: it must be pure black/white at 10% precisely because it must *not*
   pick up the engine's hue-tinted neutrals. Rare, and each one needs
   justifying in the stylesheet.

**"Change this hex" is never a valid recommendation** — it would be overwritten
on the next generate. Any colour finding must be routed to one of the three
above.

**Verifying a route-1 change needs CI.** The Rust toolchain is not available in
the agent environment (org policy, not a missing binary), so an engine-input
change cannot be validated where the design work happens — you can reason about
it, but you cannot see the ramp it produces.

That gap is now closed by the **Harmoni ramp audit** workflow
(`.github/workflows/ramp-audit.yml`), which runs
`crates/harmoni-core/examples/ramp-audit.rs` and publishes the result. Run it
by hand (`workflow_dispatch`) on whatever branch carries the engine change, read
the summary in the run, and download the `ramp-audit` artefact to diff a
before-run against an after-run. It reports:

1. **Reproduction** — whether each ramp still regenerates from its seed and
   matches `palette.json` step for step.
2. **Quality metrics** — hue span, light-end lightness spacing, chroma peak:
   the three measurements the findings below turn on.
3. **The full per-step L/C/H table**, so two runs are directly comparable.

Quality is **reported, never gated** — a gate would block the very commits
trying to improve a ramp. Only reproduction can fail the run, and only when
explicitly asked (`strict`), because a palette that no longer regenerates from
its seeds always means something is out of sync.

This also fixed a gap the audit surfaced incidentally: **the palette had no
recorded inputs**. The seeds were entered interactively in the Figma plugin and
only the output was ever committed, so the ramps were not reproducible from the
repo at all. They now live in `packages/tokens/harmoni-seeds.json`, and the
workflow verifies they are correct rather than trusting them.

Until a run exists, treat the route-1 findings below as **diagnosed but
unverified**: the measurement of the *current* ramp is solid, the proposed
remedy is not yet tested. Route-2 and route-3 findings are unaffected — they are
pure token edits and are verifiable without the engine.

# 2026-08-15 — `better-ui`

Sixteen principles, checked against both halves of the system. Roughly half
are static and decidable in Figma (concentric radius, optical alignment,
shadows-vs-borders, image outlines, icon treatment); the other half exist
only in CSS (interruptible transitions, scale-on-press, `will-change`,
transition specificity, theme-switch suppression). A Figma-only review would
silently skip eight of them, so both surfaces were swept.

**Scope:** 62 registry components · `packages/tokens/src` resolved across 4
density modes × 5 size slots · `packages/icons` (48 glyphs) ·
`apps/workbench/src/pages` · Figma file `1Nh5ffky0lYEw0MzXoqQVy`.

## Summary

| | Count | Notes |
| --- | ---: | --- |
| High | 0 | Nothing makes an interaction misleading or unresponsive. |
| Medium | 6 | Craft and consistency; most affect many components at once. |
| Low | 3 | Isolated polish, concentrated in the icon layer. |
| Verified clean | 6 | Including 120/120 on focus-ring concentricity. |
| Not applicable | 3 | Motion-library principles; the registry ships no motion dependency. |

The headline is good news. Focus-ring geometry is **exactly concentric across
every component, size and density mode in the system**, and the motion layer
is more disciplined than most codebases manage. The findings cluster around
images, press feedback, and one inconsistency in how floating surfaces define
their edge.

## Verified clean

Worth recording explicitly — four of these are the result of deliberate
engineering and would be easy to erode by accident later.

- **Focus-ring concentricity.** 30 focus-ring stems × 4 density modes,
  resolved through the alias chain. Every one satisfies `gap = base + 2` and
  `ring = base + 4` against `focus.ring.offset` / `focus.ring.width`.
  **120/120, zero drift.** Slider and Radio use `radii.full` throughout,
  correct for a circular thumb.
- **Transition only what changes.** 112 transition declarations across the
  registry; **zero** instances of `transition: all` or
  `transition-property: all`. Every one names its properties.
- **Interruptible animations.** Only 10 `@keyframes` in 62 components, all
  correctly scoped: one-shot directional panel enters (navigation-menu,
  stepper), an infinite loader (progress), and scroll-driven `linear both`
  effects (carousel parallax, cover-flow). Interactive state changes all use
  transitions. Every animation carries a `prefers-reduced-motion` guard.
- **Sparing `will-change`.** No declarations at all; the only match in the
  registry is a carousel comment explaining its deliberate absence.
- **One SVG, recoloured per state.** `IconBase` sets `fill="currentColor"`
  for all 48 glyphs; states come from CSS colour. No per-state assets.
- **Shadow colour neutrality.** `shadow.color.{soft,medium,strong}` are pure
  black at 4/6/8% — not tinted neutrals — so elevation stays honest on both
  grounds. The same discipline the image-outline fix needs.

## Not applicable

`initial={false}` on `AnimatePresence`, staged enter stagger, and subtle exit
transitions all assume a motion library the registry deliberately does not
ship — there is no `motion` or `framer-motion` dependency. Recorded as
not-applicable rather than passing.

## Verification

- **Token arithmetic, resolved not assumed.** Parsed `context.json`,
  `primitives.json` and `interaction.json`, followed every `{alias}` chain to
  a literal, and computed the concentric relationships across all 4 density
  modes × 5 size slots. Findings quote resolved pixel values, not token names.
- **Two numbers were corrected mid-audit.** The Dropdown row inset was first
  taken from `panel.padding-block`; reading `dropdown/styles.css:175` showed
  the inline axis uses a flat `space-4`. Recomputing moved that finding from
  "20/20 wrong" to **12/20 correct** and dropped it from Medium to Low. The
  Card finding was likewise held back until `card/styles.css:304` confirmed
  `margin: var(--primitiv-card-padding)` — the media really is inset by the
  full padding.
- **Registry swept in full.** All 62 component stylesheets grepped for
  `transition`, `@keyframes`, `will-change`, `:active` transforms, image
  selectors and outline declarations. Every count in this document comes from
  those sweeps.
- **Figma inspected live** over the Desktop Bridge (probe 3 ms). Rendered the
  Card set (`1444:37322`, 30 variants) and the Avatar set (`433:7944`, 30
  variants). The Avatar render is the direct evidence for the image-outline
  finding; the Card render confirms the inset-media geometry.

### Still to verify

- **Motion was reviewed as source, not replayed** at 10% speed in the
  browser's Animations panel. The theme-switch smear is predicted from the
  source, not observed.
- **Optical alignment was not measured on rendered controls.** The Button
  finding is derived from the symmetric `padding-inline` and confirmed by
  Simon from experience; the exact per-size inset values are a proposal and
  want a browser check before they land as tokens.
- **Icon centring inside Icon Button** (a square control with a single
  centred glyph) is the other classic optical case and was not checked.

## Verdict

**Needs changes.** Six Medium and three Low findings remain; no High. Nothing
here is misleading or unresponsive — the foundations are unusually
disciplined, and the focus-ring result is something most design systems never
achieve at all.

If only one thing gets done: the **image outline**. It is a handful of lines,
it affects Avatar, Card, Carousel and Figure at once, and the Avatar render
shows the system already looks inconsistent with itself without it.

If two: add `framed-control/{size}/icon-optical-inset`, since it is already a
known problem and the token family it belongs to is well established.

# 2026-08-15 — `better-accessibility`

Fourteen principles, walked keyboard-first then screen-reader-first across the
headless library, the registry stylesheets, and the kitchen-sink surface.

**Scope:** `packages/react/src` (headless semantics, focus management) · 62
registry components · `packages/tokens/src` resolved across 4 density × 5 size
· `apps/kitchen-sink`.

## Summary

| | Count | Notes |
| --- | ---: | --- |
| High | 1 | Focus indicators vanish entirely in forced-colors mode. |
| Medium | 4 | Hit areas, scroll containment, a missing autoplay control, page structure. |
| Low | 2 | Disabled styling and one stray selector. |
| Verified clean | 9 | The semantics layer is in genuinely good shape. |

The library's *semantics* are strong — native elements throughout, correct
live-region primitives, real label wiring, APG keyboard patterns, and a
`@media (hover: hover)` gate on **24 of 24** hover-styled components. The
findings are concentrated in **rendering modes and sizing**, not in markup.

## Findings

### Visible focus rings

| Severity | Location | Before | After | Why |
| --- | --- | --- | --- | --- |
| **HIGH** | `registry/components/button/styles.css:276`<br>and every one of the 28 components that draws a focus ring | `:focus-visible { outline: none; box-shadow: 0 0 0 <offset> <surface>, 0 0 0 <offset+width> <ring>; }` — **zero** `forced-colors` blocks exist across all 62 components | Add to the shared ring recipe:<br>`@media (forced-colors: active) { outline: 2px solid Highlight; outline-offset: 2px; }` | **Browsers strip `box-shadow` entirely in forced-colors mode** (Windows High Contrast). The `outline: none` survives. The net result is that a keyboard user in forced-colors gets **no visible focus indicator anywhere in the system** — every button, input, tab, tree row and menu item. The two-layer box-shadow ring is otherwise excellent work (it follows the control's radius and stays concentric at every size, verified 120/120 in pass 01); it just needs a forced-colors fallback beside it. This is one shared recipe, so it is one fix, not 28. |

### Minimum hit area

| Severity | Location | Before | After | Why |
| --- | --- | --- | --- | --- |
| MEDIUM | `packages/tokens/src/context.json` → `framed-control/{size}/height` | `dense/xs` = **16px**, `dense/sm` = **20px**, `compact/xs` = **20px** — square icon-only controls at these sizes are below the floor | Either raise the three to 24px, or document them as opt-in with a spacing requirement, or extend the hit area with a pseudo-element while the visible control stays small | WCAG 2.5.8 (AA) sets a 24×24 CSS-pixel floor. **3 of 20** density × size combinations fall under it, and an Icon Button is square so height *is* the target. The 24px exceptions (spacing, inline, equivalent-control, essential) may cover specific usages, but as shipped defaults these three are a documented risk rather than a considered choice. The remaining 17 combinations pass, and everything at `comfortable` and `spacious` clears 24 comfortably. |

### Trap and restore focus

| Severity | Location | Before | After | Why |
| --- | --- | --- | --- | --- |
| MEDIUM | `registry/components/modal/styles.css`<br>`registry/components/drawer/styles.css` | Neither declares `overscroll-behavior` | `overscroll-behavior: contain` on the scrollable content region of both | Dropdown, Combobox, Select and Carousel all get this right — Modal and Drawer, the two components where it matters most, do not. Scrolling to the end of a modal's body chains to the page behind it, so the background moves under an open dialog. The focus trap itself is sound: Modal uses a native `<dialog>` (which inerts the background) plus a boundary-only Tab-wrap in `useModalContent.ts` and focus restore on close. |

### Structure is navigation

| Severity | Location | Before | After | Why |
| --- | --- | --- | --- | --- |

### Disabled states and selectors

| --- | --- | --- | --- | --- |
| LOW | `registry/components/button/styles.css:287` and the other components using the shared disabled recipe | `[data-disabled] { opacity: var(--primitiv-opacity-50); }` | Replace the opacity with a **semantic re-binding** — point `action/*/disabled/foreground` and `/background` at existing steps of the generated neutral ramp (route 2 above, no engine change) — plus a `forced-colors` branch using `GrayText` | Opacity-only disabled styling multiplies text contrast by 0.5, which takes otherwise-passing label text well below any threshold, and opacity is unreliable as a state signal in forced-colors mode. ## Verified clean

The semantics layer is the strongest part of the system and is worth recording
in detail, because most of it would be easy to erode.

- **Hover gated for touch — 24 of 24.** Every component with `:hover` rules
  wraps them in `@media (hover: hover)`. No sticky hover states after a tap.
- **Native elements throughout.** No `<div onClick>`, no `role="button"`
  anywhere in the registry. Actions are `<button>`, navigation is `<a href>`.
- **Correct live-region pairing.** Both primitives exist and are used for the
  right thing: `Alert` renders `role="alert"` (implicit `aria-live="assertive"`)
  for urgent errors, `Status` renders `role="status"` (implicit polite) for
  routine updates. Most systems ship only one and misuse it.
- **Label and description wiring.** `Field` wires `htmlFor`, `aria-describedby`
  and `aria-invalid` through a shared id, so help text and error text are
  properly associated rather than merely adjacent.
- **Accessible names on icon-only controls.** Chip's remove button, Breadcrumb
  Overflow's trigger and Modal's close all carry `aria-label`.
- **Focus trap and restore.** Modal uses a native `<dialog>` — the background
  is genuinely inert, not just visually covered — with a boundary-only Tab-wrap
  and focus restored to the trigger on close.
- **Reduced motion.** Every one of the 10 `@keyframes` and all transition-driven
  open/close animations carry a `prefers-reduced-motion` guard (carried over
  from pass 01, re-confirmed here).
- **Autoplay semantics.** Carousel flips `aria-live="off"` while autoplay runs,
  so auto-advance does not spam a screen reader, and `PlayPauseTrigger` throws
  if used without autoplay enabled — a correct API guard.
- **Text resize.** Font sizes emit in `rem`, so browser text-size settings and
  200% zoom both work rather than being pinned by `px`.

## Verification

- **Focus mechanism traced to source.** Confirmed the ring is
  `outline: none` + two-layer `box-shadow` by reading `button/styles.css:276-283`,
  then grepped all 62 stylesheets for `forced-colors` and `-ms-high-contrast`
  — **zero matches**. The HIGH finding follows from the CSS spec behaviour of
  `box-shadow` under forced colors, which is well-established, not from a
  rendered test.
- **Hit areas computed, not eyeballed.** Resolved `framed-control/{size}/height`
  through the alias chain for all 4 density modes × 5 sizes and compared each
  against the 24px floor.
- **Semantics swept across both layers.** Grepped `packages/react/src` and
  `registry/components` for live-region roles, `aria-label`, `htmlFor`,
  `aria-describedby`, `aria-invalid`, `role="button"`, `<div onClick>`,
  `overscroll-behavior`, `@media (hover: hover)` and bare `:focus`.

### Still to verify

- **No screen reader was run.** Every semantic finding here is from source, not
  from NVDA / JAWS / VoiceOver output. The live-region behaviour in particular
  (principle 11 notes that dynamically inserted alerts have inconsistent
  support) needs testing against real assistive tech before being called done.
- **No forced-colors rendering test.** The HIGH finding is derived from spec
  behaviour; confirming it takes a Windows High Contrast session or Chrome's
  forced-colors emulation.
- **Keyboard walkthrough not performed interactively.** APG conformance was
  read from the headless implementations and their tests, not driven by hand.
  NavigationMenu's deliberate non-roving tabindex (correct for a disclosure
  nav) is the kind of decision that source review catches and a naive automated
  check would flag wrongly.
- **200% zoom / 320px reflow unverified.** `rem` font sizing is a good signal
  but not proof; the kitchen-sink's fixed-position TOC is the most likely
  reflow casualty.

## Verdict

**Block.** One HIGH finding remains: focus indicators disappear entirely in
forced-colors mode, across the whole system. That makes the interface
unusable by keyboard for anyone relying on high-contrast rendering, and it is
a single shared fix rather than 28 separate ones.

Everything else is Medium or below, and the semantics layer underneath is
genuinely strong — this is a rendering-mode gap in an otherwise well-built
accessibility story, not a systemic problem.

## Findings

### Tabular numbers on changing values

| Severity | Location | Before | After | Why |

## Verified clean

- **The heading scale is textbook.** Sizes descend monotonically (48 · 40 · 32
  · 28 · 24 · 20) and the line-height ratio *loosens* as size drops — 1.167 at
  h1 through 1.4 at h6 — which is exactly right: large type needs tighter
  leading, small type needs more. No level can overpower its parent.
- **Everything emits in `rem`.** Font sizes and line-heights both, so browser
  text-size preferences and 200% zoom work rather than being pinned by `px`.
- **No raw-tag misuse.** Zero `font-variation-settings` and zero
  `font-feature-settings` anywhere — the system uses real CSS properties, which
  keep working when a non-variable fallback renders.
- **Uppercase is styled, not typed.** All four uppercase labels (dropdown,
  context-menu, listbox, select) use `text-transform: uppercase` in CSS, so
  copy stays in natural case.
- **Small caps get their tracking.** Those same labels bind
  `--primitiv-letter-spacing-wide`, which is the half of principle 8 that most
  systems miss. (The heading half is the LOW finding above.)
- **The `<abbr>` hint is correct.** `text-decoration-style: dotted` marks
  extra-information words, precisely the convention the principle describes.
- **Truncation exists where rows can overflow** — combobox, listbox, select,
  tree and miller-columns all handle it rather than letting text escape.

### A considered deviation, not a finding

Line-heights are **absolute (`rem`), not unitless**. The principle prefers
unitless so leading scales with the element's font size. Here the tokens ship
as font-size/line-height *pairs* and every ratio is correct, which is a
defensible system-level choice (Tailwind does the same). Worth knowing the one
failure mode it creates: a consumer who overrides only
`--primitiv-input-font-size` — without also overriding
`--primitiv-input-line-height` — gets broken leading, where a unitless value
would have adapted. Documenting the pairing requirement is probably enough.

## Verification

- **Type scale resolved, not read.** Followed `heading.h1`–`h6` and
  `body.xs`–`xl` through the alias chain to literal `rem` values, then computed
  every line-height ratio to check the hierarchy.
- **Measure quantified.** Read Container's `lg` cap (`64rem`) and divided by
  `body-md` (16px) to get the ~128-character figure, after confirming Prose's
  stylesheet is 54 lines with no width constraint at all.
- **Registry swept in full.** All 62 stylesheets grepped for
  `font-variant-numeric`, `text-wrap`, `text-transform`, `letter-spacing`,
  `text-decoration`, `text-overflow` / `line-clamp`, `font-variation-settings`
  and `font-feature-settings`.

### Still to verify

- **Nothing was read at real content lengths.** The measure finding is
  arithmetic; the wrapping findings are from absent declarations. Both want the
  viewport resized against real copy to see where lines actually break.
- **No macOS rendering comparison** was made for the font-smoothing finding.
- **The typefaces were not evaluated.** Khand (headings) / Asta Sans (text) /
  JetBrains Mono are loaded from Google Fonts and the pairing was not assessed
  for contrast or suitability — that is a design judgement rather than a code
  finding, and worth a deliberate look if it has never had one.

## Verdict

**Needs changes.** Four Medium and three Low, no High.

The scale underneath is the strongest foundation of the three passes so far —
nothing here is *wrong*, and several findings are one declaration against a
token that already exists. Start with `tabular-nums`: six components, one
property, and it removes visible layout jitter that a user notices without
being able to name it.

# 2026-08-15 — `better-layout`

attention to direction-independence, since the system already ships RTL

**Scope:** 62 registry components · the breakpoint scale · `Container`, `Grid`,
`Drawer` and `Carousel` as the layout-owning components.

| | Count | Notes |
| --- | ---: | --- |
| High | 0 | |
| Medium | 3 | Text growth, container-level adaptation, safe areas. |
| Low | 3 | Breakpoint provenance and two physical-direction leftovers. |

**The direction-independence work is exemplary** and worth stating plainly:
**zero** `margin-left`, `margin-right`, `padding-left`, `padding-right`,
`border-left` or `border-right` across all 62 stylesheets, against 588

### Plan for growth and clipping

## Verified clean

- **Logical properties, essentially perfect.** Zero physical
  `margin-*`/`padding-*`/`border-*` left/right declarations across 62

- **The four remaining `left:`/`right:` are legitimately physical.**
  `context-menu/styles.css:187–196` positions a menu against a **pointer

- **The scroll affordance exists as a first-class knob.** Carousel ships

  kept separate so the resting track shows no accidental peek — the hidden-content
  cue is a designed feature, not an afterthought.
- **No fixed dimensions on prose or text-flow containers.** The 134
  `height`/`block-size` declarations are on controls, icons, tracks, thumbs and
  media boxes; the only problematic ones are the six controls filed above.

- **Container-query claim checked twice.** The single `@container` grep hit

### Still to verify

- **The 2× grouping rule was not measured.** Principle 1 asks that inter-group

## Verdict

**Needs changes.** Three Medium and three Low, no High.

The foundation here is the best of the four passes — the logical-property

## Findings

### Measure the rendered pair, then report

> **Revised after the first ramp-audit run (see the addendum below).** These
> were originally filed as route-2 re-bindings. They are better understood as
> one **engine capability gap**, and the re-binding is a mitigation rather than
> the fix.
>
> The engine is not silent on contrast. Every `Swatch` carries
> `best_foreground`, a `ForegroundSource`, and a `contrast_result` — and across

> `SoftWhite`, `SoftBlack`, `PureWhite`, `PureBlack`. It draws from the ramp's

>
> So those three roles are hand-picked in the semantic tier, with nothing
> checking them. That is why they drifted below threshold silently, and it is

  pairs (Alert, Badge, Tag) and every hover/active state were not, and hover
  states are where a passing default often slips under.
- **No rendered check.** Contrast was computed from tokens; nothing was
  screenshotted and sampled, so any opacity applied at render time — notably
  the `opacity: 0.5` disabled recipe from pass 02 — is not reflected in these
  numbers and will measure worse.

## Addendum — measured against the live engine

Everything above was measured against the **committed** palette, because the
Rust toolchain is unavailable here. The `ramp-audit` workflow now runs the real
engine, and the first two runs changed several conclusions. Corrections first.

### Colour problems belong to Harmoni

The framing that makes the rest of this coherent: **Figma and the CSS are
carriers.** Neither invents a colour — both receive whatever the engine emits.
So a defect in a ramp is an engine defect, and a token-tier edit that papers
over it is a mitigation, not a fix. The three re-bindings above are worth doing
because they stop shipping failing contrast today; they are not the answer to
why those values were wrong.

### The engine holds hue perfectly — the gamut mapping does not

| ramp | theme | hue span **intended** | hue span **rendered** |
| --- | --- | ---: | ---: |
| brand | light | 0.0° | 15.6° ⚠ |
| brand | dark | 0.0° | **31.2°** ⚠ |
| danger | light | 0.0° | 6.0° |
| danger | dark | 0.0° | 6.5° |
| warning | light | 0.0° | 33.4° ⚠ |
| warning | dark | 0.0° | 22.8° ⚠ |
| success | light | 0.0° | 0.9° |
| success | dark | 0.0° | 1.6° |
| info | light | 0.0° | 6.0° |
| info | dark | 0.0° | 2.6° |

**Intended is 0.0° everywhere.** The engine's ramp definition is not the
problem — it holds hue exactly, on every ramp, in both themes. All drift is
introduced when the colour is quantised into the sRGB gamut, so the fix belongs
in the OKLCH→sRGB mapping. That is the same machinery RFC 0010 already tightened
once (the `linear_in_gamut` tolerance change from `±1e-3` to `1e-5`).

### Two corrections to my own findings

**`info` is already fixed, and the finding was stale.** I filed it at 22.1°
drift. Current engine output is **6.0° / 2.6°** — comfortably inside the
threshold. The committed `info` ramp simply predates an engine improvement.

**I missed `brand` dark entirely, and it is the worst ramp in the system at
31.2°.** My pass-05 script measured light ramps only, so a drift worse than
`warning` dark went unreported — and unlike warning, this one *does* reproduce
from the current engine, so it is live in the shipped tokens. Brand is also the
most-used ramp (38 aliases). This should outrank the original warning finding.

### The committed palette is stale for three ramps

| ramp | reproduces from its seed? |
| --- | --- |
| brand | yes (1 step differs by one unit — quantisation, not drift) |
| danger | yes (1 step, same) |
| warning | **no** — 8 steps differ materially in light, 6 in dark |
| success | **no** — 8 steps in light, 6 in dark |
| info | **no** — differs in both |

The seeds in `harmoni-seeds.json` are correct (brand and danger reproduce
exactly), so this is not a manifest error — `warning`, `success` and `info` were
generated by an older engine and never regenerated. **Regenerating is its own
fix**: it resolves `info` outright and improves `warning` from 38.7° to 33.4°.
Nothing in the repo currently detects this; the workflow now does.

### The engine's accessibility guarantee is complete — within its scope

Across all 100 generated swatches: **zero `Fail` ratings, 72 AAA, 28 AA.** Every
swatch the engine produces has a guaranteed-accessible foreground, and that
guarantee holds even on the defective ramps — the warning ramp's hue drift never
produces an unreadable fill.

The limit is scope, not quality. `ForegroundSource` returns `Step900`, `Step50`,
`SoftWhite`, `SoftBlack`, `PureWhite` or `PureBlack` — ramp ends and anchors,
answering *"what text goes on this fill"*. The roles that failed (link, muted
text, border) are mid-ramp-step-on-a-different-surface, which the engine has no
API for. **That gap is the real finding behind all three contrast failures**,
and closing it would make the whole class impossible rather than fixing three
instances.

### What this changes about priority

1. **Regenerate the palette.** Free, fixes `info`, improves `warning`, and
   removes the stale-snapshot problem. Verify with a `ramp-audit` run.
2. **Investigate `brand` dark at 31.2°** — worst ramp, most-used ramp, live in
   the shipped tokens, and not previously reported.
3. **Extend the engine's foreground API** to cover mid-ramp-on-surface roles, so
   the semantic tier consumes a guarantee instead of a hand-picked step.
4. **Re-bind the three failing pairs** as a stopgap while 3 is built.
5. **Gamut mapping** is the root cause of all hue drift — the deepest fix and
   the one to scope last.

## Verdict

**Needs changes.** Four Medium and three Low as filed, plus one previously
unreported ramp defect (`brand` dark) surfaced by the first engine run.

The token architecture remains the best result in the whole audit — the
primitive/semantic seam is not violated once in 62 stylesheets. And the engine
is in better shape than the committed palette suggests: it holds hue exactly,
and it guarantees an accessible foreground for all 100 swatches with zero
failures.

Start by **regenerating the palette**. It costs nothing, fixes one finding
outright, improves another, and stops three ramps shipping from an engine
version nobody is running any more.
